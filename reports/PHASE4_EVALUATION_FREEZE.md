# Phase 4 Evaluation Freeze Report

## What is frozen

Four new evaluation suites, generated by `python -m juniper_math dataset
eval-suites-build` (`src/juniper_math/dataset/eval_suites.py`), **before**
the training corpus was built (Sec. 12 — see "Order matters" in
`docs/DATASET.md`). The existing Phase 0 suite (`evals/phase0_v1.json`, 22
cases) remains frozen and unmodified; these are additional, independent
suites, not a replacement.

tens per category) are well within even the smallest categories'
combinatorial capacity, unlike the much larger per-category token targets
the training corpus draws against.

## Ground-truth verification

Every case in every suite passed the same construction-time verification
the training corpus uses (`juniper_math.dataset.build.ground_truth_ok`):
deterministic cases are recomputed via
`juniper_math.dataset.verify.evaluate_expression` and compared against the
recorded `expected_answer`; tool cases are executed against the real Phase
3 `ToolRuntime` and the recorded `tool_traces` are that execution's actual
output; semantic cases (ambiguity/missing/undefined/unsupported) are
checked for classification consistency (`expected_answer` must be `null`).
A case that failed this check was never written to the suite file — there
is no manual override path.

`tests/test_dataset.py::test_generators_produce_valid_ground_truth`
exercises the same generator functions these suites are built from as an
ongoing regression check.

## Contamination isolation from the training corpus

Three independent layers (see `docs/DATASET.md` "Contamination
prevention"):

1. Disjoint seed namespace (`config/dataset.yaml`'s
   `eval_suite_seed_offset`, folded with a per-suite-name offset).
2. `dataset build` pre-seeds its exact/near deduplicators with every eval
   example on disk, structurally excluding train-corpus collisions.
3. `dataset contamination-check` independently re-verifies both layers held
   for the actual built corpus — result: **zero** exact or near-duplicate
   overlap between any of the 725 eval cases and any of the 1,833,697
   training-corpus examples (see `reports/PHASE4_DATASET_VALIDATION.md`).

This is not merely a claim: an earlier build (before the reservation
mechanism in `build_dataset`'s `eval_reserved_examples` was added) DID
produce ~20 exact eval/train collisions in the low-diversity categories
(ambiguity, undefined_operation, tool_error, etc.) — the contamination
checker caught it, the fix (seeding the dedup structures with eval-suite
content before generation starts) was implemented and verified, and the
final full-scale run confirms zero contamination.

## Why these suites use a different schema than the Phase 0 baseline

`juniper_math.dataset.schema.Example` (the same record schema as the
training corpus), not `juniper_math.evals`'s narrower schema. See
`docs/EVALUATIONS.md` "Why a different schema from the Phase 0 suite" —
Phase 3 already established the precedent that different evaluation suites
may have different, purpose-fit schemas
(`evals/phase3_tools_v1.json` is not loaded by `juniper_math.evals` either).

## Status

All four suites are frozen at `suite_version: "1.0.0"`. Any future edit to
their cases requires a version bump and hash regeneration, exactly as the
Phase 0 suite's versioning policy already requires
(`docs/EVALUATIONS.md` "Freezing and versioning").
