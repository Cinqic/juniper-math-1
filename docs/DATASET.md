# Dataset (Phase 4)

Canonical spec: [`config/dataset.yaml`](../config/dataset.yaml). This file
documents what that config means and how to use the pipeline that reads it —
exactly the same relationship `docs/TOOLS.md` has to `config/tools.yaml`.

## Identity

- `dataset_id`: `juniper-math-dataset-v1`
- Built against `juniper-math-tokenizer-v1` (frozen Phase 2) and
  `juniper-tool-protocol-v1` v1.0.0 (frozen Phase 3) — both identities are
  recorded in `config/dataset.yaml` so a version drift in either fails loudly
  rather than silently changing what a token or a tool result means.
- `master_seed: 20260401` — every generator/family/example seed derives from
  this via SHA-256 (`juniper_math.dataset.idgen`), never from Python's
  `random` module's global state and never from `hash()` (which is
  `PYTHONHASHSEED`-randomized per process).

## Scope decision: synthetic-only

v1 uses **zero external sources**. All 24 categories are generated by
project-controlled, seeded Python generators under
`src/juniper_math/dataset/generators/`. This was a deliberate, conservative
call (not an oversight) for reasons recorded in
[`reports/PHASE4_PROVENANCE_LICENSE_REVIEW.md`](../reports/PHASE4_PROVENANCE_LICENSE_REVIEW.md):
independently establishing that a third-party math corpus's license actually
covers redistribution of its *data* (not just its repository's code) is a
legal-judgment call this engineering session is not positioned to make
responsibly, and the Phase 4 instructions themselves warn against including
a dataset "merely because everyone else trains on it." A future dataset
version may add vetted external sources; that is out of scope for v1.

## Category schema

Every generated record is a `juniper_math.dataset.schema.Example` — one of
24 categories (`VALID_CATEGORIES`), one of 4 difficulties, one of 7
`expected_behavior` values (the exact same vocabulary the frozen Phase 0
`juniper_math.evals` module already uses: `answer`, `request_clarification`,
`refuse_unsupported`, `flag_missing_information`, `flag_undefined`,
`flag_incorrect_answer`, `invoke_tool`), and a `verification` block whose
`mode` is one of:

- **`deterministic`** — ground truth is recomputed from an explicit
  `expression` tree via `juniper_math.dataset.verify.evaluate_expression`, a
  closed-allowlist evaluator (`add, sub, mul, div, neg, abs, pow,
  percent_of, ratio, round, sqrt, max, min, lt, le, gt, ge, equals`) that
  never calls `eval`/`exec`/`compile`. This is deliberately a *separate*,
  broader allowlist from the frozen Phase 0 evaluator
  (`juniper_math.verification`, 8 operations) — that module is frozen
  infrastructure scoped to the 22-case Phase 0 suite and is not touched by
  Phase 4.
- **`semantic`** — no single answer exists (ambiguity, missing information,
  undefined math, unsupported capability). `expected_answer` is always
  `null` for these, matching the Phase 0 convention exactly.
- **`tool`** — ground truth comes from actually executing the real Phase 3
  `ToolRuntime` (never a fabricated `<tool_result>` string). The literal
  call/result pair is recorded in `tool_traces`.

Every example also carries `example_id`, `generator_id`, `generator_version`,
`family_id`, `template_id`, `derivation_id`, and `seed` — the provenance
fields Sec. 6 of the Phase 4 instructions asks for (where did this come
from, how was it verified, which split can it enter).

## The 24 categories and their generator modules

| Module | Categories |
|---|---|
| `generators/arithmetic.py` | arithmetic, operator_precedence, negative_values, decimals, fractions, scientific_notation, estimation, numerical_comparison, expression_translation, basic_algebra |
| `generators/percent_ratio.py` | percentages, ratios_proportions |
| `generators/tools.py` | unit_conversion, financial_math, tool_use, incorrect_tool_call, tool_error |
| `generators/word_problems.py` | word_problem, multi_step |
| `generators/semantic.py` | ambiguity, missing_information, undefined_operation, unsupported_capability |
| `generators/errors.py` | incorrect_supplied_answer |

`generators/registry.py` aggregates all of these; `python -m juniper_math
dataset build` fails loudly at startup if any of the 24 categories has no
registered generator.

### Deliberately small categories

`ambiguity`, `missing_information`, `undefined_operation`,
`unsupported_capability`, and `tool_error` have small
`category_mixture` shares (0.4–1%, vs. 3–13% for most categories). This is
not an oversight: these are curated, construction-verified template
families (Sec. 10) with inherently bounded combinatorial diversity (a
handful of names/small integers/scenario shapes). An early full-scale build
showed these categories plateau on exact-duplicate space long before a
proportional share of the token envelope — exactly the Sec. 18 "don't force
size past a quality plateau" signal. `config/dataset.yaml` documents this
inline.

## Pipeline

```bash
python -m juniper_math dataset acquire              # reports: zero external sources (honest, not skipped)
python -m juniper_math dataset eval-suites-build     # freeze the 4 Phase 4 eval suites FIRST (Sec. 12)
python -m juniper_math dataset build                 # generate -> verify -> clean -> dedup -> split -> shard -> stats
python -m juniper_math dataset validate               # schema-validate every record in the built shards
python -m juniper_math dataset verify                 # recompute ground truth + re-execute every tool call live
python -m juniper_math dataset stats                  # print the recorded statistics
python -m juniper_math dataset contamination-check     # split isolation + eval/train overlap check
```

`dataset generate` is a documented alias of `dataset build` (Sec. 20 lists
them as separate concerns, but for a 100%-synthetic v1 dataset there is no
meaningful "generate raw data, then separately build shards" split — a
future external-source version might reintroduce that distinction).

### Order matters: eval suites are frozen before the training corpus

Per Sec. 12, `dataset eval-suites-build` must run **before**
`dataset build`. `dataset build` loads whatever eval suite files currently
exist under `evals/phase4_*.json` and seeds the exact+near deduplicators
with their prompts before generating a single training example
(`juniper_math.dataset.build.build_dataset`'s `eval_reserved_examples`
parameter) — so anything exactly or nearly matching a frozen eval case is
structurally excluded from train/validation/test by the same dedup
machinery that already keeps the corpus itself clean, not a second,
separately-maintained exclusion list. `dataset contamination-check`
independently re-verifies this held (actual prompt-similarity comparison,
not just seed-namespace trust) — see "Contamination prevention" below.

## Splits

Train/validation/test assignment (`juniper_math.dataset.split.assign_split`)
is a deterministic hash of `(generator_id, family_id, derivation_id)` —
**never** row order and never Python's `random` module. Every example
sharing a `derivation_id` (the same underlying problem instance, possibly
rendered with different surface phrasing) lands in the same split.
`dataset contamination-check`'s
`check_derivation_id_isolation` re-verifies this held for the actual built
corpus.

## Deduplication

- **Exact**: SHA-256 of `(normalized_prompt, expected_answer)` — implemented
  in `juniper_math.dataset.dedup.ExactDeduplicator`, tracked corpus-wide.
- **Near**: shingled Jaccard (5-word shingles, 0.92 threshold by default —
  see `config/dataset.yaml`), implemented in `NearDeduplicator`. This is
  deliberately a bounded, family-scoped check (each family keeps only its
  most recent 200 examples in its comparison window) rather than full
  corpus-wide pairwise comparison, which is quadratic and impractical at
  multi-million-row scale. This bound is a documented trade-off (Sec. 17
  "no silent caps"), not a hidden one — see
  `juniper_math.dataset.dedup`'s module docstring.

## Anti-template-collapse

`config/dataset.yaml`'s `diversity_caps.max_template_share_within_family`
(0.60) caps how much of a family's accepted examples any single
`template_id` may account for once that family has produced at least 30
examples. 0.60, not a stricter value, because several families have only
2–3 phrasing templates by design (Sec. 8 explicitly warns against inflating
template counts with meaningless wording churn) — a cap below `1 /
template_count` for any real family would make convergence mathematically
impossible.

## Token budget

`config/dataset.yaml`'s `token_budget` declares the Sec. 18 working envelope
(50–100M tokens, target 70M) — a target, not a quota. `dataset build`
reports `shortfall_categories` honestly when a category's exact-duplicate
space is exhausted before its proportional token target, rather than
inflating operand ranges into unnatural territory to force convergence.
Every token count uses the frozen `juniper-math-tokenizer-v1` tokenizer,
applied to `juniper_math.dataset.shard.render_training_text`'s rendering of
each example (prompt + any `<tool_call>`/`<tool_result>` traces +
`<final>`/behavior tag) — never characters, words, or another model's
tokenizer.

## Sharding

JSONL shards under `data/processed/juniper-math-dataset-v1/` (gitignored —
see `.gitignore`'s `data/processed/*` rule; disposable, reconstructible from
this repository's generators/config alone). Deterministic ordering (sorted
by `example_id`, never iteration/insertion order), deterministic shard
boundaries (`records_per_shard: 50_000`), and a shard manifest
(`shard_manifest.json`) recording per-shard record count, token count, byte
size, and SHA-256. The whole-dataset identity
(`DATASET_IDENTITY.sha256`) is the SHA-256 of the ordered concatenation of
every shard's own SHA-256 — never a hash of a directory listing, which is
filesystem-order dependent.

## Contamination prevention

Defense in depth, three independent layers:

1. Eval-suite generation uses a seed namespace disjoint from
   train/validation/test (`config/dataset.yaml`'s
   `split.eval_suite_seed_offset`, folded with a per-suite-name offset in
   `juniper_math.dataset.eval_suites`).
2. `dataset build` pre-seeds its exact/near deduplicators with every eval
   suite example currently on disk, so the corpus build itself cannot
   produce a train example that exactly or nearly matches a frozen eval
   case.
3. `dataset contamination-check` independently re-verifies both of the
   above after the fact (`derivation_id` split isolation, exact cross-split
   duplicates, and near-duplicate eval/train prompt pairs), plus catches any
   residual overlap the seed-namespace and dedup-seeding layers missed.

## Statistics and hashing

`dataset build` writes `data/processed/juniper-math-dataset-v1/stats.json`
(category/difficulty/behavior/tool distributions, token percentiles,
build-rejection counters). `python -m juniper_math hash verify` covers the
frozen Phase 4 artifacts recorded in `manifests/artifacts.yaml` — the
dataset config, the four eval suite files, and the corpus's own
`DATASET_IDENTITY.sha256` file (the shards themselves are gitignored and
disposable; their identity is what's frozen, not their bytes in Git).

## Rebuilding

The entire corpus reconstructs from nothing but this repository:

```bash
rm -rf data/processed/juniper-math-dataset-v1
python -m juniper_math dataset eval-suites-build
python -m juniper_math dataset build
```

Two independent builds from the same commit produce byte-identical shards
and an identical `DATASET_IDENTITY.sha256` — see
[`reports/PHASE4_DATASET_VALIDATION.md`](../reports/PHASE4_DATASET_VALIDATION.md)
for the actual rebuild evidence, not just this claim.
